2What PR #7 changes

2.1  Prisma — one file per module

The single apps/server/prisma/schema.prisma is replaced by a schema folder, so each domain owns its own file and two students editing different models no longer collide in the same file.

Two gotchas that cost real time — please don't re-discover them

Prisma 6.19 does not auto-detect a schema folder. The path must be declared explicitly; it now lives in apps/server/package.json under the prisma key. This prints a deprecation warning pointing at prisma.config.ts. That migration was deliberately deferred: a config file disables automatic .env loading and would need a dotenv dependency.

Migrations move with the schema. With a schema folder, Prisma resolves migrations relative to that folder, so prisma/migrations/ is now prisma/schema/migrations/. Leave it in the old place and the CLI reports every existing migration as missing and demands a database reset.

2.4  Three implementation details worth knowing

  • Decimal → number. Prisma returns Decimal instances that JSON-serialize as strings, which silently breaks arithmetic in the browser. Both services map them to numbers before returning. Any new module reading price should do the same.
  • Column-to-column filtering. onSale compares compareAtPrice > price using Prisma field references inside where. Filtering in JS after the query would corrupt total and produce short pages.
  • Deactivate, don't delete. Products referenced by an OrderItem cannot be deleted; the API returns a message telling the admin to deactivate instead. This protects order history — directly relevant to FEATURE-005.

2.5  Admin panel and storefront

  • Admin gains real Categories and Products pages (full CRUD, category filter, modal forms) built on the tokens already in styles.css. They replace the placeholder pages.
  • AdminLayout used Tailwind classes that do not exist in the admin theme — bg-bg, bg-surface, border-border, text-text, text-star — while styles.css defines --color-admin-*. They compiled to nothing, leaving the background, body text, panel surfaces and header border unstyled. Now mapped onto the tokens that exist.
  • apps/client/src/components/home/data.ts is deleted. Category nav, category grid, hero rails, flash sale and trending rows all read from the API.
  • The catalog page gains search, sort and pagination and serves both /products and /category/:slug; /products/:slug is now a real product detail page.
  • Cross-app navigation was missing entirely: the admin sidebar gains View storefront, and the storefront top bar gains Home and Admin. Separate origins, so these are plain anchors driven by VITE_STOREFRONT_URL / VITE_ADMIN_URL.

2.6  Web push over VAPID

  • A PushSubscription row per browser, so one account can be reached on several devices. The endpoint is unique, so re-subscribing the same browser updates its keys instead of piling up duplicate rows.
  • Delivery is best-effort: a failed send never fails the request that triggered it, and subscriptions the push service reports as gone (404/410) are pruned automatically.
  • The app still boots without VAPID keys — push simply reports itself disabled, so nobody needs a keypair just to run the catalog. Generate a pair with web-push and put it in apps/server/.env (see .env.example).
  • Endpoints: GET /api/notifications/vapid-public-key (public), subscribe / unsubscribe, list, unread-count, mark one or all read, and POST /api/notifications/broadcast (admin).
  • The client registers public/sw.js, which renders the push and focuses an existing tab on click rather than opening a duplicate.

2.7  Storefront content the admin now owns

  • Flash sale. The countdown used to be a hardcoded 04:32:15 that never moved. It now runs down to a real end time, and the strip’s headline, end time and visibility are set on the new admin Marketing page. Which products appear is still automatic — anything whose compare-at price exceeds its price.
  • Newsletter. The form submitted nowhere. There is now a NewsletterSubscriber table, public subscribe / unsubscribe and an admin list. Sign-up is idempotent, and the response deliberately does not reveal whether an address was already on the list.
  • Dashboard. It displayed invented figures — a hardcoded “+12.5%”, zero products, “Latency: 24ms”. It now reads a real /api/admin/stats endpoint.

2.8  Toasts and other gaps closed

  • A shared ToastProvider in both apps: auto-dismissing stack, success / error / info tones, aria-live (assertive for errors), and an entrance animation gated behind motion-safe. Inline banners are kept for form validation errors, which belong next to the field rather than in a corner.
  • /help, /support and /sell were linked from the header and top bar but had no routes, so they fell through to the 404. All three now render.
  • The header search box did nothing; both the desktop and mobile inputs are now forms that navigate to /products?q=….
  • The catch-all route redirected silently to /, hiding genuinely dead links. Replaced with a real 404 page.
  • The profile page showed only what was cached at login; it now re-reads /auth/me and surfaces role, join date and unread notifications.
  • Logout only reset authApi, so the next account could briefly see the previous user’s cached notifications. All user-scoped caches are cleared.
  • AdminLayout referenced Tailwind classes absent from the admin theme (bg-bg, bg-surface, border-border, text-text, text-star), which compiled to nothing and left the panel unstyled. Mapped onto the --color-admin-* tokens that exist.

2.9  Shopping cart — wired, not reimplemented

Add to Cart did nothing, the badge was hardcoded to 0 and /cart had no route. Rather than write a third parallel implementation, the cart module, its DTOs and its unit test are ported verbatim from feat/kenule-shopping-cart (PR #5) and registered in AppModule, so the two branches converge instead of colliding the way #4 and this branch do over categories.

The two-carts decision is now made

Kenule’s client-only features/cart/cartSlice.ts and PR #5’s server cart were two competing sources of truth. This branch picks the server cart — the only one that can price an order from the database — and deletes the unused slice, which nothing imported. Order creation in FEATURE-005 should read from it.

  • ProductCard and ProductDetail call addItem. The card is itself a link to the product, so the button must preventDefault or every add would navigate away. Signed-out users get a prompt and are sent to login rather than a 401.
  • The detail page has a quantity field capped at the product’s stock, so the form cannot offer more than the API will accept.
  • /cart renders line items, a quantity stepper, per-line remove, empty cart, and a summary priced entirely by the server. Decrementing to zero removes the line rather than sending an invalid quantity.
  • The header badge reads the server cart, so it survives reloads and is consistent across devices.

3Running it locally

Two helper scripts sit at the repository root. Both were broken in ways that are easy to misread as “the project doesn't work”, and both are fixed in PR #7.

ScriptWhat it does
launch-webapp.batStarts the gmc-postgres container on port 5433, waits for it, runs prisma generate and migrate deploy, compiles the server once, then opens three terminals (API, storefront, admin) and polls the API before reporting success.
stop-webapp.batFrees ports 3000 / 5173 / 5174, closes the three terminals, stops the container. Data survives in the Docker volume.
Why the API used to die on launch while the two frontends came up fine

The script deleted apps\server\dist and immediately ran nest start --watch. The watcher launches dist/src/main.js the moment it appears, so against an empty dist it raced the compiler and exited with Cannot find module './app.module'. Nest only retries on a file change, so the API stayed dead and silent. It now compiles once before the watcher starts.

Two smaller fixes: timeout /t 1 aborts with “input redirection is not supported” when stdin is redirected, so the DB wait loop uses ping; and the script now warns explicitly instead of printing the URLs while the API is down.

If the API will not start

Check docker ps first. A stopped gmc-postgres makes Nest exit at boot with Prisma P1001 — Can't reach database server at localhost:5433. Note the port is 5433, not the default 5432.

Seed accounts all use Student123!: admin@example.com (ADMIN), student1@example.com, student2@example.com. Note the storefront login at /api/auth/login deliberately rejects ADMIN accounts; admins sign in at /api/admin/auth/login.

7For Raead — what FEATURE-005 can build on

Update — epic-5 is merged

Your epic-5 (reviews & ratings, real-time socket notifications, orders pages, domain events) is now merged into feat(kenule)/auth (PR #9), and the Orders API (POST /orders, GET /orders, admin status update) is live. What’s still open: the admin Orders management page — /orders in the admin app is still a placeholder, so building that status/CRUD UI is the natural next piece. The guidance below still applies.

Orders is a module plus a frontend slice. Order, OrderItem and OrderStatus already exist in Prisma, so no migration is required. Once PR #7 lands, these are ready to use:

  • A products module to read from. ProductsService already returns prices as numbers, so order totals can be computed without unwrapping Decimal yourself.
  • Stock and price on every product. stock for availability checks, price for the unitPrice snapshot on each OrderItem.
  • Deletion already protects order history. A product on an order line cannot be deleted, so OrderItem.productId will not dangle. Keep this rule in mind if you add order-side deletes.
  • An admin shell to extend. Add an Orders page next to Categories and Products; reuse the shared primitives in apps/admin/src/components/ui.tsx (Field, Input, Select, Modal, Banner) and the errorMessage helper so validation errors surface properly. The sidebar already has an /orders placeholder route to replace.
  • A guard pattern to copy. products.controller.ts is the shortest example of public reads plus admin-only writes on one controller, including the manage/all-before-:slug route-ordering rule.
Your one real decision: which cart feeds an order

This is now decided: the server cart won and the client-only slice is gone. CartService.getCart(userId) returns items with unitPrice, lineTotal and a server-computed subtotal — exactly the shape order creation needs. Branch from this PR (or from feat/kenule-shopping-cart if #7 has not merged) and you inherit a working cart to build checkout on.

Snapshot the price at purchase time

OrderItem.unitPrice exists precisely so an order keeps the price that was charged. Copy product.price into it when the order is created — never join back to Product to display a historical order, or every past order changes whenever an admin edits a price in the panel.
